# 메뉴 막대가 존재하지만 보이지 않았던 문제

## 문제 정의

쌀먹 프로세스와 메뉴 막대 접근성 항목은 존재하고 클릭 메뉴도 생성됐지만, 사용자가 보는 화면에는 아이콘이 없었다. 문제의 핵심은 “트레이 객체 생성 실패”가 아니라 “생성된 항목이 화면 밖 좌표에 배치되는 현상”이었다.

이 사건부터 메뉴 막대 기능의 완료 정의는 다음 네 조건을 모두 만족하는 것으로 고정한다.

1. 지정한 앱의 프로세스가 실행 중이다.
2. 상태 항목의 좌표와 크기가 현재 화면의 상단 영역 안에 있다.
3. 실제 화면 캡처에서 서비스 로고와 남은 숫자가 보인다.
4. 왼쪽 클릭, 오른쪽 클릭 메뉴, 갱신, 종료가 실제 포인터 입력으로 동작한다.

접근성 목록에 항목이 있다는 사실만으로는 2~4를 증명하지 못한다.

## 사용자 영향

- 백그라운드 실행과 자동 갱신은 살아 있었지만 핵심 진입점이 보이지 않았다.
- 사용자는 같은 앱을 여러 차례 다시 설치·실행했지만 결과가 달라지지 않았다.
- 개발 과정에서는 접근성 항목 존재를 화면 표시로 잘못 해석해, 원인이 아닌 아이콘 폭·저장 위치·재삽입 코드를 반복 수정했다.

## 확인한 증거

| 시험 | 관측 결과 | 판정 |
|---|---|---|
| 당시 Tauri 트레이 구현 | 접근성 항목과 메뉴는 존재했으나 프레임이 화면 하단 또는 좌측 밖에 잡힘 | 화면 표시 실패 |
| 처음 보였던 최적화 전 실행 파일 재시험 | 현재 환경에서는 똑같이 보이지 않음 | 최근 한 커밋만의 회귀가 아님 |
| 사용량 스냅샷 캐시 제거 후 재시험 | 변화 없음 | 앱 데이터 캐시 원인 아님 |
| 화면 여유 공간 측정 | 우측 메뉴 영역에 충분한 폭이 있음 | 단순 메뉴 막대 혼잡 원인 아님 |
| 순수 AppKit 최소 시험 | 같은 PNG, 같은 메뉴, 고정·가변 폭, 오버레이, Accessory 정책에서 모두 보임 | 이미지·폭·메뉴·정책 원인 아님 |
| Tauri 앱 안에서 AppKit 직접 생성·개발 빌드 | 로고와 남은 숫자가 실제 화면에 표시됨 | 1차 교체 후보 |
| 같은 코드의 Tauri 배포 빌드 | AppKit 직접 생성도 `(1653, -1)` 또는 `(-1, 1100)`에 고정 | 1차 교체는 불충분 |
| SDK 14→26, 최소 OS 14→11, 1초 지연, autosave 제거 | 모두 화면 밖 상태 유지 | 빌드 표식·시점·위치 저장 원인 아님 |
| 같은 앱 묶음 안의 별도 AppKit 실행 파일 | `(1103, 5)`에서 실제 픽셀 표시 | 프로세스 경계 확인 |
| Tauri+AppKit 도우미 통합 배포 앱 | `(1115, 5, 58×24)`에서 로고·숫자 표시 | 최종 교체 방향 통과 |

현재 확인된 원인 경계는 **Tauri 배포 런타임과 같은 프로세스에서 생성한 상태 항목**이다. Tauri `tray-icon` 경로와 AppKit 직접 생성 모두 이 경계 안에서 화면 밖 좌표를 재현했다. 반면 같은 앱 묶음 안의 별도 순수 AppKit 프로세스는 정상 배치됐다. 내부의 정확한 한 줄짜리 결함까지는 특정하지 못했으므로, Tauri 전체 하나나 macOS 자체 하나를 단독 원인으로 확대해 단정하지 않는다.

관련된 상류 사례는 [tray-icon PR 317](https://github.com/tauri-apps/tray-icon/pull/317), [Tauri issue 13519](https://github.com/tauri-apps/tauri/issues/13519), [Tauri issue 13770](https://github.com/tauri-apps/tauri/issues/13770)이다. 이 사례들은 macOS 상태 항목 위치·표시가 불안정할 수 있다는 보조 근거이며, 쌀먹에서 관측한 정확한 내부 원인을 대신하지 않는다.

## 왜 처음에는 됐나

최초 실행 때 실제로 보였다는 사용자 관측은 유효하다. 그러나 당시에는 다음 실행까지 포함한 반복 화면 증거를 남기지 않았다. 나중에 같은 초기 실행 파일을 다시 돌렸을 때도 보이지 않았으므로, 최초 성공 당시의 실행 조건과 이후 재시험 조건이 같았는지 추가 대조가 필요하다. 최초 성공이 일시적이었다고 확정할 근거는 부족하다. 정확히 어떤 macOS 상태 변화가 최초 성공을 만들었는지는 확인 불가다.

## 배제한 가설

- 빌드 캐시가 깨졌다.
- 사용량 JSON 캐시가 잘못됐다.
- 노치나 메뉴 막대 공간이 부족하다.
- PNG 색상이나 크기가 잘못됐다.
- 고정 폭과 가변 폭 중 하나가 문제다.
- 메뉴 연결이나 투명 클릭 오버레이가 문제다.
- Dock 비표시 또는 Accessory 정책이 문제다.
- 숨김 시작 순서만 문제다.
- 본창이 0개라서만 발생한다.
- macOS SDK 14로 빌드해서만 발생한다.
- 최소 지원 버전 14 설정이 문제다.
- `autosaveName` 위치 복원이 문제다.

각 항목은 같은 조건을 하나씩 적용한 순수 AppKit 시험 또는 이전 실행 파일 재시험으로 배제했다.

## 해결

- Tauri 본체는 본창, 데이터 수집, 자동 시작, 알림만 담당한다.
- 약 100KB인 별도 Swift 도우미가 AppKit의 `NSStatusBar`와 `NSStatusItem`을 소유한다.
- Tauri가 JSON 한 줄로 표시 상태를 보내고, 도우미는 `toggle`, `open`, `refresh`, `quit` 동작만 돌려보낸다.
- 부모의 입력 파이프가 닫히면 도우미도 종료되고, 도우미만 비정상 종료되면 Tauri가 2초 뒤 다시 시작한다.
- 가장 적게 남은 서비스의 공식 로고와 숫자 하나를 표시해 상단 폭을 줄인다.
- 왼쪽 클릭은 본창 열기·닫기, 오른쪽 클릭은 두 서비스의 전체 상세 메뉴를 담당한다.
- Tauri `tray-icon`, 같은 Tauri 프로세스 안의 AppKit 직접 생성, 로컬 우회 패치는 모두 제거했다.

## 재발 방지

### 자동 구조 관문

`pnpm verify`가 `scripts/check-native-tray-boundary.sh`를 먼저 실행한다. 다음 중 하나라도 생기면 CI가 실패한다.

- Tauri의 `tray-icon` 기능 재활성화
- `TrayIconBuilder`, `tauri::tray`, `with_inner_tray_icon` 재도입
- 로컬 `tray-icon` 우회 패치 재연결
- Tauri 프로세스 안의 AppKit 상태 항목 재도입
- Swift 도우미, 부모 연결 코드, 앱 묶음 설정 중 하나라도 누락

### 실제 화면 관문

설치 또는 메뉴 막대 생명주기 변경 뒤 `pnpm verify:menubar`를 실행한다.

- 다른 쌀먹 본체나 메뉴 막대 도우미가 있으면 즉시 실패한다.
- 지정한 앱을 `--hidden`으로 직접 시작한다.
- 별도 AppKit 도우미가 하나이고 상태 항목도 정확히 하나인지 확인한다.
- 시작 직후의 임시 프레임을 통과로 오인하지 않도록, 같은 화면 안 좌표가 두 번 연속 관측되는지 확인한다.
- 상태 항목 부분만 PNG로 저장해 개인정보 노출 범위를 줄인다.
- 사람이 PNG에서 로고와 남은 숫자를 모두 확인해야 최종 성공 영수증을 쓴다.
- 영수증과 PNG는 공개 저장소에 올라가지 않는 `.runtime-evidence/`에 보존한다.

### 릴리스 관문

메뉴 막대 또는 앱 생명주기를 바꾼 릴리스는 아래를 모두 확인한다.

1. 숨김 시작 직후 실제 픽셀 표시
2. 정상 종료 후 최소 두 차례 재실행에서도 실제 픽셀 표시
3. 왼쪽 클릭으로 본창 생성, 다시 클릭해 본창 파기
4. 오른쪽 클릭 메뉴에 Codex·Claude 요청 필드 전부 표시
5. `지금 갱신` 뒤 스냅샷 생성 시각 변경
6. 본창을 닫은 뒤 Tauri 본체와 AppKit 도우미 유지
7. 도우미만 종료했을 때 2초 뒤 새 프로세스로 자동 복구
8. Dock 미표시와 두 프로세스의 합산 메모리 확인
9. 설치본 실행 파일 해시와 검증한 빌드 결과물 해시 일치
10. Codex 초기화권을 소비하지 않았음을 확인
